%   ============================================================
%   SAOI warpage — LATENT CAPACITY x REGULARIZATION SWEEP
%   ARM 04/16 : vae_latent_dim 128  |  r4 (alpha_recon 10, lambda_mmd 1.0)
%   current SAOI config_train_top.txt; recon:mmd = 10:1
%
%   WHAT THIS SWEEP IS FOR
%   The b8 ablation measured posterior recon corr 0.996 against generation corr
%   -0.03: the posterior path reconstructs almost perfectly while the generative
%   path tracks the conditioning not at all. That is not a capacity shortage --
%   it is z carrying the whole answer while the graph pathway carries nothing,
%   leaving the FM prior to regress a 384-dim vector encoding the entire field
%   from geometry alone.
%
%   Two things let the encoder do that, and this sweep varies both:
%     AXIS 1  vae_latent_dim {128, 64, 16, 8} -- how many numbers z can hold.
%     AXIS 2  alpha_recon:lambda_mmd ratio {1e4, 1e3, 1e2, 1e1} -- how much the
%             objective cares about anything other than reconstruction. Note
%             clip_grad_norm_(max_norm=3.0) renormalizes the update every step,
%             so only the RATIO between terms matters, not absolute magnitude.
%
%   The interaction is the interesting part: the diagnosis predicts small z helps
%   MOST at high recon dominance (r1), because there the dimension is the only
%   thing limiting what z can carry.
%
%   Full grid: z in {128,64,16,8} x r in {r1,r2,r3,r4} = 16 arms, 2 per GPU.
%
%   SCORE WITH (not the training loss -- that measures the posterior path):
%       python misc/eval_distribution.py --config <cfg> --split test --k 50
%   Compare generation corr / CRPS / wild rate across the grid.
%
%   BUDGET. Measured: 4 GPUs at Batch_size 2 = 2.5 min/epoch, i.e. N/10 samples
%   per GPU-minute. One arm on one GPU processes all N samples => ~10 min/epoch;
%   two arms sharing a GPU => ~20 min/epoch each. Wall clock for the grid is
%   arms x epochs x 10min / 8 GPUs = 1.25 x arms x epochs minutes ~= epochs/3
%   hours at 16 arms. 1000 epochs ~= 333 h ~= 14 DAYS (the measurement was
%   taken with val_interval 1, which runs the 8-forward CRPS eval every
%   epoch; at val_interval 10 the per-epoch cost is ~9%% lower, so this is
%   conservative). The main uncertainty is the two-jobs-per-GPU contention
%   factor: at 1.7x it lands near 12 days, at 2.3x near 16 days.
%   THIS IS A TWO-WEEK RUN. best_by crps keeps the best-so-far checkpoint
%   throughout, so an early kill still leaves every arm scored on its best
%   generation metric rather than on whatever epoch it happened to reach.
%
%   DELTAS vs config_train_top.txt (identical in all 16 arms, so they cannot
%   explain a difference between arms):
%     Batch_size      2    -> 4       (2 jobs share each GPU)
%     num_workers     4    -> 2       (16 concurrent jobs; avoid worker storms)
%     val_interval    1    -> 10      (prior-path eval costs 8 forwards/batch)
%     Training_epochs and test_interval now MATCH config_train_top.txt
%     (1000 / 100), so they are no longer deltas.
%     std_noise       0.1  -> 0.01    (SEE BELOW -- this one is a real fix)
%     best_by              -> crps    (select on the generation metric)
%     hierarchy_cache_keep -> True    (16 jobs share one cache; no job may delete
%                                      it mid-sweep. DELETE IT MANUALLY after.)
%   ============================================================
